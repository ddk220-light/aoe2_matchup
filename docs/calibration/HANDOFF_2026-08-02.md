## 1. Mission

Make the JS battle engine (`apps/website/static/js/engine/`) replicate real AoE2:DE
AI-vs-AI fight recordings ("tapes"). The JS engine becomes the ONLY engine — the
Python engines (`aoe2x/sim/simulation.py`, `simulation_real.py`) get deprecated, and
the matchup table (~500k sims), rankings, UI and YouTube videos all re-derive from it.
Judge on RESULTS: winner match first, HP-remaining texture second.

**Iron rule (user, standing): NO fitted stochastic behavior constants.** Mechanisms
must emerge from real game physics with dat values, or use explicitly *measured tape
breakpoints* (documented at the constant). Tape aggregate stats are validation
targets, never injected. When a rule needs scoping, scope by measured evidence
(e.g. armor classes), not by what fixes the scoreboard.

**Workflow (user, standing):** measurement-only agents produce forensics → the main
session does all design/ideation and writes precise specs → implementation agents
execute them → iterate on fight *subsets* (3 seeds) → one full-corpus gate before any
landing. Parallelize narrow agents; never give two agents the same file region.

## 3. Findings ledger — the composed kite-escape stack (built, gated, default OFF)

The user's observation ("kiters should circle the middle, even through units — ours
end up wiped on the map edge") drove four measured rounds. Each mechanism is
implemented, flag-gated, tested, and **OFF** pending one final piece:

| Flag (constants.js) | Mechanism | Evidence |
|---|---|---|
| `E1.orbitKite` | Kite retreat waypoint = clockwise arc about the fight center (spawn-centroid midpoint) instead of radial flight | 78/78 tapes orbit CW, median +1.13 rev, radius held; engine was +0.146 t/s outward with 85% of kiter deaths at walls |
| `C3.postSwingPlant` | Melee chaser cannot move for 0.7 s after a landed swing on a ranged (non-siege, class 20 excluded) victim | Tape plant 0.64–0.74 s across 5 chaser classes, 0% halts <0.2 s; = ~100% of the kiter's +1.03 tiles/reload escape |

Mounted archers measured as already-correct (tape AI kites them poorly — that's why chasers beat them) |
| `R5D1.reducedDamageHits` (P1) | Displaced-hit half damage (unrounded, on-primary) | Tape-exact; under the stack it fixes the one siege winner miss (`hand_cannoneer__vs__heavy_scorpion`) |

Composed results (`docs/calibration/c4_flee_during_reload.md`): champion-vs-arbalester
6/6 *with the orbit on*, champion dmg/run 490 (tape band 127–603), foot run lengths
2.7–3.2 s, wall-deaths 0.56→0.14, canaries 4/4, melee byte-identical. Full board
E1+C3+C4+P1 = **195/234 vs baseline 201** — the ENTIRE deficit is
`champion__vs__heavy_cav_archer` (−7, ablation-proven to be E1's orbit geometry on
the mounted ball) +1 scorpion. Hence:

**The one missing ranged mechanism — E2 orbit-radius law (measured, not yet built).**
`docs/calibration/e2_orbit_radius_law.md` (82 tapes): the kiter does NOT control
orbit radius; it controls **nearest-enemy distance** in a band — advance toward the
nearest enemy above d\* (4.77 arb / 4.09 HC / 4.45 HCA tiles ≈ **0.6× own range**),
orbit tangentially in-band, retreat inside ~3.5. Fire-at-max-range falsified
(at-fire target distance ≈ 25% of range). Tape kiters push through enemy bodies at
collision contact (74–91% of blocked arcs); blocked widens mean-revert in ~3 s.
E1's current "preserve current radius" waypoint is a **ratchet** (avoidance shoves
accumulate) — replacing it with the setpoint band kills the balloon by construction.
Spawn-radius cap is the recommended guard. **Truth note:** `champion__vs__heavy_cav_archer`
= HCA wins 8/9 (the tape ball survives mid-field at r≈3–4 feeding champions partial
damage); the current baseline engine is already right there, the orbit stack broke it
by wall-wiping the ball, and the band law is expected to restore it.

**Rejected this campaign (do NOT rebuild):** orbit blend with away-vector (radial
duplicate), C2A kiter break-on-hit (refuted solo AND in composition), C2B
stop-to-swing, P2 `trailingWindowLead` (re-breaks champ-vs-arb even with the full
stack — stays blocked), keep-enemy-at-max-range radius law, r-at-last-fire ratchet,
E13-style fitted churn constants, melee-vs-melee plant (step function refuted; tape

## 4. Findings ledger — melee

- **Paladin-vs-steppe resolved as truth, opened as engine bug.** New position-valid
  recordings: paladin wins 20/24 (11/12 live-position rounds) — the old
  "steppe wins 5/6" tapes were bad captures (quarantined; now in `to_delete/`).
  Engine picks steppe every round. `docs/calibration/ps_live_forensics.md`: the
  opening is exact (concurrency, ring density, attackers-per-victim med 2/p90 4/max 6
  identical), the defect is **paladin re-engagement** — a blocked paladin whose
  locked victim is out of reach parks (idle 28.8% of living frames vs tape 6.8%;
  moving 5.7% vs 22.8%) → steady concurrency 4.24 vs 6.19 → fight drags 55 s vs 46 s
  = exactly the ~530 HP of paladins that should survive. Lane rule exonerated twice.
  Same defect family as champion-vs-paladin's outnumbered-side 0.73× engagement.
- **The fix (W1, partially implemented — see §7): scrum-flow walk.** Blocked
  out-of-reach melee attacker drifts tangentially around the blocking mass (direction
  = less-obstructed side; arc step = own speed×dt; zero new constants). Targets:
  concurrency →~6.2, idle →~7%, duration →~46 s, paladin wins ≥9/12; invariants:
  the 2/4/6 attackers-per-victim ceiling and steppe ~3.9 hits/s (already exact).
- **Determinism caveat:** pure melee draws no RNG and the live rounds share
  byte-identical spawns → the engine has effective sample size 1 per melee family
  while the game itself spans a spread (steppe+6 … paladin+8). Don't over-read
  per-family winner counts.
